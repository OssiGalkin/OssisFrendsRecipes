# API Management (built-in) vs API Portal (add-on)

**Keep these apart.** API Management ships with every Tenant: it is how a Process is exposed and secured as an API. **API Portal** is a separately purchased add-on for publishing APIs to external developers.

API Management built for Frends 6.3.x from: `/reference/api-management/api-policies.md`, `/release-notes/frends-6.3/breaking-changes` (full read), `/reference/api-management/api-specifications.md`, `/reference/triggers/http-trigger.md`, `/reference/frends-platform-api/platform-api-reference/models.md` (ApiPolicy*, DtoApiKey* schemas), `/get-started/frends-glossary.md`. Not traversed this build: `/reference/api-management/passthrough-apis.md`, `api-monitoring.md`, the `/guides/api-management/` guides, the migration guide, if any (the migration is described from the Breaking Changes page below).

## API definitions

- An API is an OpenAPI document in the API editor (OpenAPI **3.1.1** and 3.0.x supported; 2.0 for legacy). Each operation is fulfilled by a Process with an **API Trigger** or by a **Passthrough** configuration.
- `servers[0].url` is the base path: must start with `/api/`, unique per Agent Group; further servers and per-path server overrides are ignored functionally.
- One Process links to exactly one API operation and has exactly one API Trigger; share logic through Subprocesses.
- Parameters and responses are not binding: extra request parameters are reachable with `[ ]`, missing ones arrive as `null`; Return may diverge from the spec without validation errors (not recommended).
- Versioning is automatic: each saved spec change bumps the patch version, each deployment bumps the **major** version; deployed versions are immutable.
- **`securitySchemes` / `security` are documentation only.** Runtime authentication, throttling and access control come from **API Policies**, which change without editing or redeploying the spec.
- HTTP Trigger is the lightweight alternative (no OpenAPI); its Authorization options are **API Policy** (default), **Basic** (not on Cloud Agents) and **Certificate**. "Public – will be accessible on API Gateway" exposes it through the Gateway.

## API Policies

- **No policy, no access**: every endpoint reachable from outside the Agent needs at least one policy; there is no implicit public access.
- Parts: `Name` (required, unique in the Tenant), `Description`, `Tags`, **Targeted endpoints** (method incl. `ALL` + free-text path + optional throttling), **identities**, optional **logging configurations**.
- **HTTP Trigger endpoints** do not appear in the endpoint dropdown but are governed by policies: type the path and pick **"Create /your/endpoint"**.
- **Path matching**: segment-based prefix match, case-insensitive; `/api/v1/crm` matches `/api/v1/crm/customers/123` but not `/api/v1/crmadmin`; `{id}` matches one segment and everything beneath. The page states that trailing slashes are normalised, and in a hint that a trailing slash on a policy path (`/api/v1/foo/`) **can block a more explicit sub-path definition from resolving** — remove trailing slashes. Both statements are on the same page.
- **Inside one policy**: the more exact path wins regardless of method; at the same path an explicit method beats `ALL`.
- **Overlap**: each method + path can be covered by only one policy per Agent Group; overlaps are flagged at save.
- **Identity scopes**: **API Key** — keys (Administration > API Keys) are scoped to an **Environment** (`DtoApiKeyCreate.environmentId`); header or query, shared throttle per identity; separate policies for one endpoint across Agent Groups of one Environment can conflict — the page suggests a Private Application token instead. **OAuth** — issuer from Administration > OAuth applications, bearer token, `Targeted Agent Groups`, claim rules `Exists` / `Exact` / `Regex` (all must pass). **Private Application** — issuer is the Tenant; not Environment-scoped; Agent Group targeted; same claim rules. **Public Access** — Agent Group targeted; **from 6.3** combinable with other identities in one policy. **Before 6.3.3** an Agent Group that received the policy for another reason (an OAuth identity, an API key, request logging) also accepted anonymous requests; from 6.3.3 public access applies only to the Agent Groups selected for it, and callers that relied on the old behaviour get 401/403 after the next heartbeat. The API model also carries `priorityNumber` per identity (lower wins when several identities match).
- **Evaluation order**: OAuth token → API Key → Public Access, only for configured methods. A parseable OAuth token is final (insufficient claims → rejected even with a valid key); an unparseable one is ignored; a valid OAuth token against a policy without OAuth may yield **403** even with a valid key.
- **Logging configuration** (per Agent Group): without one, **no API connection logs**. Fields: Identity (default), Query Parameters (truncated at 1000 chars), Request Headers (no `Authorization`), Response Headers, Error Response Body, Request/Response Body (cap 1 / 10 / 100 KB, default 1). IP logging: Client IP, X-Forwarded-For first, X-Forwarded-For all, Disable. This covers API connection logs only; Process logs follow the log settings.
- Throttling: per endpoint and per identity (`requestLimit` + `requestLimitWindowInMinutes`).
- A logging-only policy can coexist with authentication policies; different Agent Groups can each have their own policy for the same endpoint.
- 6.3.3: users whose Environment rules exclude an Environment a policy targets no longer see that policy, and cannot update or delete it — including the default request-logging policies, which target every cross-platform Agent Group. IPv6 callers now match only IPv6 entries in `PlatformJwtAllowedIps` or an OAuth provider's allowed networks.
- **Migration from the pre-5.8 model** (listed on the 6.3 Breaking Changes page): an API Process with OAuth in its OpenAPI spec whose path was also in an API Key ruleset becomes reachable by **both** methods; the old API-key headers (`Authorization: Apikey`, `x-apikey`, spec-defined header) are replaced by a configurable header, with the old configuration still read as a fallback when no policy exists for the key; inconsistencies between the OpenAPI spec and Process deployments can block the update. That is all the page states about what the migration produces.
- How to *organise* policies is judgment, not covered here.

## API Portal add-on

Built from `/api-portal/general/preparing-your-frends-api-for-publishing` (full read) and search excerpts of `/api-portal/general/` pages: getting-started, how-to-create-api-products, how-to-use-api-products, admin-roles-and-user-management, changing-users-role-in-api-portal, audit-log-and-security. Not read: customization/look-and-feel pages, API Portal release notes.

- A separate portal where **API Products** — one or more API operations from the connected Tenant — are published to organizations and users.
- **Products**: public or private visibility; **access control tags** limit which organizations see a product; a **Production Environment** must be chosen for every product, with an optional **Sandbox**; **Require approval for access** makes users request access and an administrator approve before a token is issued.
- **Roles**: **Portal Administrator** (whole portal: all organizations, users, audit logs, portal settings) and **Organization Administrator** (own organization: invite/remove users, product access and subscription requests, organization settings). Creating an organization makes you its administrator; a private account can later become an organization.
- **Tokens — the Frends side of the work**: on access, the portal creates one **Private Application per organization** in your Tenant (via the Platform API; it only creates, never modifies or deletes existing Private Applications or tokens) and issues one token per API Product carrying the **`ApiProductId`** claim. You configure an API Policy: Public access **off**, a **Private Application identity** targeted at the right Agent Groups, and a claim rule on `ApiProductId` — **Exists** to accept every product with one policy, or per-product matching. Needs Editor role or `ApiPolicy.Edit`.
- **The page disagrees with itself and with the policy reference**: it says the rule is case-sensitive and must be written exactly `ApiProductId`, then later writes `apiproductid`; it offers **Exact, Contains, Regex** matching, while the API Policies reference lists **Exists, Exact, Regex**. Use `ApiProductId` and the reference's operators.
- Frends validates expiry, issuer and audience by default. Revoke via the portal's organization management or manage the Private Applications in Administration.
- API Product usage is logged in the Tenant, not the portal audit log; automated token/Private Application operations may appear in Tenant logs.
